# linux_script (Resource)

Manages an arbitrary resource through commands that are uploaded to the host and executed there in each phase of the Terraform lifecycle.

## Example Usage

```terraform
locals {
  package_name = "apache2"
}

resource "linux_script" "install_package" {
  lifecycle_commands {
    create = "apt update && apt install -y $PACKAGE_NAME=$PACKAGE_VERSION"
    read   = "apt-cache policy $PACKAGE_NAME | grep 'Installed:' | grep -v '(none)' | awk '{ print $2 }' | xargs | tr -d '\n'"
    update = "apt update && apt install -y $PACKAGE_NAME=$PACKAGE_VERSION"
    delete = "apt remove -y $PACKAGE_NAME"
  }

  environment = {
    PACKAGE_NAME    = local.package_name
    PACKAGE_VERSION = "2.4.18-2ubuntu3.4"
  }

  triggers = {
    PACKAGE_NAME = local.package_name
  }
}
```

## Schema

### Required

- `lifecycle_commands` (Block List, Min: 1, Max: 1) Commands uploaded and executed on the remote host in the matching phase of the Terraform lifecycle. For long scripts, use the `file` function. (see [below for nested schema](#nestedblock--lifecycle_commands))

### Optional

- `__dirty_output__` (String) Internal state used by the provider to detect changes of `output`. It cannot be set.
- `__faulty_output__` (String) Internal state used by the provider to mark failed `read` commands. It cannot be set.
- `environment` (Map of String) Environment variables available to each lifecycle command.
- `interpreter` (List of String) Interpreter used to run each lifecycle command, as a program followed by its arguments. The path of the uploaded script is appended as the last argument. When empty, the script is executed directly, using its `#!` line or `/bin/sh`. The script is uploaded readable by the connecting user only, so an interpreter that switches user, such as `sudo -u`, cannot read it. Changing it follows the rules described in [Updating the instructions](#updating-the-instructions).
- `provider_override` (Block List, Max: 1) SSH connection settings used by this object instead of the provider configuration, as a workaround for dynamic providers. It accepts the same arguments as the provider plus an `id`, which identifies the connection in the connection pool and for locking. (see [below for nested schema](#nestedblock--provider_override))
- `sensitive_environment` (Map of String, Sensitive) Like `environment`, but marked sensitive so Terraform hides the values in its output. On a duplicate name, the value defined here wins. The provider keeps the values out of its own logs, error messages and the internal `__faulty_output__` and `__dirty_output__` attributes; the map itself is stored in state, marked sensitive. They are still part of the command line executed on the host, where other local users can see them in the process list while a lifecycle command runs, and a command that prints them can expose them in `output`.
- `triggers` (Map of String) Values whose changes force the resource to be recreated, like `triggers` of `null_resource`.
- `working_directory` (String) Directory in which each lifecycle command runs. It is created if it does not exist. Defaults to `.`.

### Read-Only

- `id` (String) The ID of this resource.
- `output` (String) Standard output of the `read` commands.

### Nested Schema for `lifecycle_commands`

Required:

- `create` (String) Commands executed in the create phase.
- `delete` (String) Commands executed in the delete phase.
- `read` (String) Commands executed in the read phase and after `create` or `update`. Their standard output is recorded in `output`, and a change in it triggers an update or a recreation. If they fail, the resource is considered absent and is planned for recreation, and in that case `delete` is not executed. Before applying, either accept that the resource is gone, fix the host so the commands succeed, or update them. They should not write anything, or at least be safe to retry.

Optional:

- `update` (String) Commands executed in the update phase, with the previous `output` available on stdin. To keep plans consistent, especially when `output` is a dependency of other objects, they should leave `output` as `create` would on a resource that does not exist. When omitted, any detected change recreates the resource instead.

## Updating the instructions

This resource differs from a regular one: besides the data that describes the actual resource, it holds the instructions to create, read, update and delete it. `lifecycle_commands` and `interpreter` are the instructions, and the other arguments are the data. Changing the instructions needs special handling, otherwise unwanted things would happen, such as the `update` commands running when only the `delete` commands changed.

When `lifecycle_commands` or `interpreter` change, the current `read` commands are first run with the existing interpreter, which is unavoidable, and then the new `read` commands are run if they changed. No other argument may change in the same apply, or an error is raised. Once the change is applied, the next run uses the new instructions and the other arguments can be changed again.
